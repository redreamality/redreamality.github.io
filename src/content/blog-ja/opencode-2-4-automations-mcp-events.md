**結論から：** OpenCode 2.4 では、agent が自分で仕事を予約できる。決まった時刻、cron、または MCP server からのイベントで、prompt、Code Mode スクリプト、固定の shell コマンドをバックグラウンドで実行する。TUI を開いておく必要はない。[1][3] 先に知っておきたい点が三つある。まず、shell アクションの承認は作成時の一度だけで、以後の実行では確認しない。後から shell ルールを `deny` にしても、作成済みのものは止まらない。次に、MCP 接続はまず 2026-07-28 の新プロトコルを試す。エラーコードを返さない古い server だと数秒余計に待つ（実測で約 5.8 秒）。最後に、`^1.0.0` や `@latest` と書いたプラグインは、起動時と 24 時間ごとに自動で更新され、再起動なしで読み込み直される。

| 状況 | やること |
| --- | --- |
| アップグレードしたい | `opencode upgrade` か `npm i -g @opencode/cli@2.4.1`。2.4.0 は macOS 12 でアシスタントのメッセージを保存できないので、2.4.1 にする。[2] |
| agent に勝手に予約させたくない | 設定に `"automations": false`。一覧は空になり、作成はエラー、既存の項目も発火しない。 |
| automation は使うが shell は抑えたい | `shell` を `ask` にすると、作成時に一度確認が出る。承認済みのものを止めるには `/automation` か API で pause か delete。ルール変更では止まらない。 |
| 無効にしてから戻した | 既存の項目は自分では復帰しない。一つずつ pause して resume するか、削除して作り直す。 |
| 古い MCP server の接続が遅い・つながらない | `mcp.servers.<名前>` の下に `"protocol": "legacy"`。v1 のフラット形式 `mcp.<名前>` に書くと無視される。 |
| プラグインを `@latest`、`^x.y.z`、Git ブランチで指定している | 自分で更新されるようになった。止めたいなら正確なバージョンを書く。 |
| GitHub Copilot を `GITHUB_TOKEN` で使っている | `COPILOT_GITHUB_TOKEN` を設定するか、OAuth でログインし直す。2.4 から `GITHUB_TOKEN` は読まない。[7] |
| 権限ルールに `experimental_image_generate` がある | ルールは `generate_image` に自動で読み替えられる。保存済みの「常に許可」は読み替えられないので、一度だけ再確認が出る。[1] |

## automation の中身

automation はトリガーとアクションでできている。トリガーは四種類。`at` はある時刻に一度、`every` は一定間隔、`cron` は五つのフィールドの cron 式とタイムゾーン、`event` は MCP server が送ってくるイベント。アクションは三種類。`prompt` はセッションに文章を送ってモデルに任せる。`code` は Code Mode スクリプトを実行し、`shell` は固定のコマンドを実行する。後の二つはモデルを通らない。[1][3]

スケジューラは server プロセスの中にある。`opencode serve` をバックグラウンドで起動し、TUI は開かずに `every 1 minute` の shell アクションを登録したところ、毎分タイムスタンプが書き込まれた。server を再起動しても項目は残り、そのまま動き続ける。実行のたびに `runCount`、`lastOutcome`、`lastOutput` が記録される。shell アクションの出力は `Exit code: 0` で始まり、その後にコマンドの stdout が続く。

API には制限が二つある。最短間隔は 1 分で、`30 seconds` は `every must be at least 1 minute` で弾かれる。shell アクションはどこかのセッションに属している必要があり、`sessionID` がないと `A shell action needs a session` になる。タイムゾーンを省くとマシンのローカルタイムゾーンが使われる。

![HTTP で automation を作成：最短間隔とセッション必須の二つの制限、毎分書き込まれるタイムスタンプ](/assets/opencode-2-4-automations-mcp-events/automation-http-limits.webp)

TUI の `/automation` はパネルではなく prompt のテンプレートだ。モデルが受け取るのは「このプロジェクトの automations を管理せよ、`automation` ツールを使え……一行で返答」という指示で、そこからモデルが `automation_create` や `automation_list` を呼ぶ。こちらの言葉はモデルの解釈を経て設定になるので、作成後は `automation_list` か API で、保存されたトリガーとコマンドを確かめたほうがいい。

## shell アクションの確認は作成時の一度だけ

リリースノートには、shell アクションは作成時に一度だけ承認を求める、とある。[3] `shell` ルールを `ask` にして、TUI でモデルに「毎分 heartbeat.txt に時刻を追記する」automation を作らせると、`Permission required` が表示され、その下に実行するコマンドが出た。選択肢は `Allow once` と `Reject` だけで、「常に許可」はない。Allow once を選ぶと、コマンドは毎分実行され、確認は二度と出なかった。

![TUI で shell automation を作るときの確認。選択肢は Allow once と Reject だけ](/assets/opencode-2-4-automations-mcp-events/tui-automation-permission.webp)

ここでの「once」は作成の一回を指し、以後の実行はすべてその承認に含まれる。automation は人がいないときに動くものなので、毎回確認していたら使い物にならない。理屈は通るが、その結果として権限ルールが効くのは作成の瞬間だけになる。

ルールを `"effect": "deny"` に変えると、新しい shell automation の作成は `Permission denied: shell` で拒否された。ところが作成済みのものは毎分動き続け、`runCount` も増え続けた。止めるには、その automation 自体を pause するか delete するしかない。

![shell を deny にすると新規作成は拒否されるが、既存の shell automation はそのまま動く](/assets/opencode-2-4-automations-mcp-events/shell-deny-existing-automation.webp)

`"automations": false` は全体のスイッチだ。設定すると一覧 API は空配列を返し、作成は `Automations are disabled. Set automations to true in config to enable them.` になり、期限が来た項目も発火しない。項目自体は削除されず、データベースに残る。

問題は有効に戻したときだ。`false` を消して再起動しても、無効の間に期限が来た項目は `lastOutcome` が `disabled` のまま、`nextDueAt` も過去の時刻で止まっていて、自分では復帰しない。毎分動く shell automation が二つとも止まったままだった。片方を pause してから resume すると次の分から動き出し、もう片方は止まったままだった。このとき shell ルールはまだ `deny` だったが、resume は拒否されず、再開したコマンドも実行された。resume でも権限は確認し直されない。

![automations: false では一覧が空になり作成も拒否される。有効に戻すと、過去の nextDueAt で止まる項目がある](/assets/opencode-2-4-automations-mcp-events/automations-false-reenable.webp)

まとめると、OpenCode の shell 承認は「ある種類の操作」ではなく「一つのコマンド」を承認する。監査するときは `permissions` だけでなく、automation の一覧そのものを見る必要がある。

## MCP イベント：server が送り、OpenCode が一回動く

2.4.0 のもう一つの柱が MCP Events だ。MCP のイベント拡張（`io.modelcontextprotocol/events`、SEP-3415）に沿っていて、まだベータ段階にある。[4][12] 拡張が定める配信方式は、クライアントによるポーリング、server からのプッシュ、webhook の三つ。OpenCode はこのうちプッシュ配信に対応し、引数チェック、ハートビート、自動再接続を備えるとしている。[1]

試験用に、`ticket.created` というイベントをプッシュ配信で宣言する stdio server を書き、モデルに「新しいチケットが来たら tickets.md に追記する」automation を作らせた。モデルが `automation_create` を呼ぶと、OpenCode はまず `events/list` でイベントの種類を確かめ、購読ごとに長く開いたままの `events/stream` リクエストを送る。server は `notifications/events/active` で購読を確定し、30 秒ごとのハートビートを取り決める。その後 server にチケットを一件入れると、イベントが `notifications/events/event` で届き、OpenCode は automation を作ったセッションに prompt を送り、モデルが T-1 をファイルに書き込んだ。

OpenCode 2.4.1 はどちらのハンドシェイクでもイベント拡張を宣言する。Claude Code 2.1.331 も `server/discover` を先に試すが、イベント拡張は宣言しない。Codex 0.172.0 は `initialize` でバージョン 2025-06-18。Gemini CLI 0.71.1 と Qwen Code 0.28.4 は 2025-11-25 だった。この二つは `mcp list` のヘルスチェックで得た結果で、実際のセッションでは確かめていない。

利用者に響くのはフォールバックのコストだ。古い server が知らないメソッドを受け取ったら `-32601` を返すのが作法で、そうすれば OpenCode はほぼ即座に `initialize` に戻る。知らないメソッドに何も返さない server もあり、その場合 OpenCode はタイムアウトまで待つ。実測では `server/discover` から戻るまで約 5.8 秒かかった。こういう server には `"protocol": "legacy"` を書く。

この設定には落とし穴が二つある。一つは、新しい `mcp.servers.<名前>` 形式でしか効かないこと。v1 のフラット形式 `mcp.<名前>` に書くと黙って無視され、プローブはそのまま行われ、ログにも何も出ない。もう一つは、`"2026-07-28"` と書くと固定モードになること。server が対応していなければ `no fallback in pin mode` で失敗し、古いほうには戻らない。

なお、公式の MCP ドキュメントは現時点でデフォルトを `legacy` と書いている。これは 2.4.0 のアップグレードノート、設定スキーマ（デフォルト `auto`）、実測のどれとも合わない。[10] リリースノートと実際の挙動を基準にしたほうがいい。

## プラグインは自分で更新し、壊れていたら戻す

2.4.0 から、バージョンに追従するプラグインは自分で更新する。`name@latest`、バージョン範囲（`name@^1.2.0` など）、Git ブランチ、Git の `semver:` 範囲で書いたものは、起動時と以後 24 時間ごとに確認され、条件に合う新しい版があればインストールして再起動なしで読み込み直す。範囲の外には出ない。新しい版の読み込みに失敗したら、前の版が動き続ける。正確なバージョン、バージョンなしのパッケージ名、`@next` のような別のタグ、Git タグ、コミットは自動更新されない。[1][6][11]

ローカルに npm registry を立て、読み込み時に自分のバージョンを出力するだけのプローブ用プラグインを公開した。設定は `oc-ver-probe@^1.0.0` で、比較用に `oc-ver-pinned@1.0.0` も並べた。

気をつけたい点が二つある。再読み込みのとき、固定バージョンのプラグインも、版は変わらないのに読み込み時の処理がもう一度走った。読み込み時にポートを開く、ファイルを書く、外部の webhook を登録するといったプラグインは、二度実行されても困らない作りにしておく必要がある。もう一つは確認結果の表示が食い違うこと。同じ時点で、API の `/api/plugin/check` は `outdated: true` を返したのに、コマンドラインの `opencode plugin check` は `(current)` と表示した。

自動更新とは、サードパーティのプラグインの新しい版が、知らないうちに OpenCode と同じ権限で agent プロセスの中で動き出すということでもある。出どころに自信のないプラグインは、バージョンを固定して `opencode plugin update` で手動で更新したほうがいい。

## アップグレード時に気づくその他の変更

**Copilot が `GITHUB_TOKEN` を読まなくなった。** git のツールや GitHub Actions はこの変数をよく設定するが、Copilot の権限があるとは限らないからだ。[7] `GITHUB_TOKEN` だけを設定した状態で、2.3.2 の provider 一覧には `github-copilot` が出て、2.4.1 では出ない。`COPILOT_GITHUB_TOKEN` を設定すると戻る。Copilot を使う CI は変数名の変更が必要になる。

![GITHUB_TOKEN だけだと 2.3.2 は github-copilot を表示し、2.4.1 は表示しない。COPILOT_GITHUB_TOKEN で戻る](/assets/opencode-2-4-automations-mcp-events/copilot-token-env.webp)

**画像ツールの改名と動画ツールの追加。** `experimental_image_generate` は `generate_image` になり、`generate_video` が加わった。動画はバックグラウンドでレンダリングされ、server を再起動しても続き、完成するとワークスペースに保存されて agent が起こされる。[1][8] どちらも、接続中の provider に画像や動画のモデルがあるときにしか出てこない。今回使った無料モデルにはないので、実行していない。

**プラグインの読み込みが再びバックグラウンドになった。** 起動直後は、モデルや provider などのエンドポイントが読み込み済みの分だけを返すので、空の一覧になることもある。使い捨てのスクリプトは自分で待つか、`plugin.list` をポーリングする。[1]

**TUI は新デザインが既定になった。** `opencode` テーマは新しいテーマを指す。以前の配色にしたければ `opencode-classic` を選び、以前のレイアウトにしたければ TUI の設定で `experimental["new-designs"]: false` にする。[9]

**Claude Code 2.1.331** の `/loop` と CronCreate はセッション単位だ。セッションが開いている間だけ動き、`--resume` で期限切れでないタスクが戻る。最短 1 分、一つのセッションで最大 50 件。繰り返しタスクは 30 日で期限切れになり（2.1.330 より前は 7 日）、`CLAUDE_CODE_DISABLE_CRON=1` でスケジューラ全体を止められる。セッションから切り離すにはクラウドや Desktop の定期タスクを使う。イベントについては、CI の失敗などを MCP のイベント拡張ではなく Channels でセッションに送り込む。[13][14]

**Codex 0.172.0** は定期実行を Codex App に置いている（cron かスレッドのハートビート）。CLI には管理用のコマンドがない。`codex features list` では `in_app_local_automation` が stable、`wake_on_agent_messages` は開発中だった。[15]

**Qwen Code 0.28.4** には `cron_create`、`cron_list`、`cron_delete`、`loop_wakeup` があり、`experimental.cron` は既定で有効。既定ではタスクは現在のセッションの中だけで生き、繰り返しタスクは 7 日で期限切れ（`cronRecurringMaxAgeDays`、0 で無期限）、`QWEN_CODE_DISABLE_CRON=1` ですべて止まる。[16]

**Gemini CLI 0.71.1** はパッケージ内に定期実行のツールが見当たらず、リリースノートにも記載がない。[17]

**Amp** にはスレッド単位のスケジュール（RRULE、スレッドごとに一つ）があり、GitHub CI などのイベント購読や webhook にも対応し、Amp のクラウドで動く。[18] 今回はログインしていないので未検証。

![各パッケージから定期実行のツールとスイッチを探した結果](/assets/opencode-2-4-automations-mcp-events/other-harness-schedulers.webp)

並べてみると、OpenCode の立ち位置は少し特殊だ。「手元のマシンに常駐する」「MCP のプッシュを受ける」「shell を直接実行する」の三つを一緒に持っているのは OpenCode だけだった。Claude Code と Qwen の定期実行はセッションに付いていて、閉じれば止まる。Codex と Amp は、持続する定期実行をアプリやクラウドに置いている。OpenCode はローカルの server に置くので、手元のファイルに触れ、セッションに依存しない。その代わり、管理はすべて手元に落ちてくる。誰が何を作り、何を実行し、何を承認したのかは、自分で確認するしかない。

## automation を使う前に決めておきたいこと

1. `shell` を `ask` にする。既定のルールでは、HTTP で shell automation を作っても確認は一切出ない。
2. `permissions` だけでなく、automation の一覧もときどき見る。承認済みの shell コマンドは、ルールを変えても止まらない。
3. イベント型 automation の prompt は狭く書き、決まった一つの作業だけをさせる。触らせたくないツールは `deny` ルールで塞ぐ。
4. MCP server のプロトコル実装に自信がなければ、`mcp.servers` 形式で `"protocol": "legacy"` を書く。
5. 本番環境のプラグインはバージョンを固定する。

前回は [OpenCode 2.3.2 が system prompt を developer メッセージに移した話](/ja/blog/opencode-2-3-2-gpt-6-2-prompt-cache-prefix/)、その前は [OpenCode 2.3 がサブ agent、時間のかかるコマンド、圧縮をバックグラウンドに移した話](/ja/blog/opencode-2-3-background-subagents-shell-compaction/)だった。MCP server が増えたときのツール選択は [MCP server の増殖と大規模なツール選択](/blog/mcp-server-sprawl-tool-selection-at-scale/)（英語）、Claude Code のコアループの全体像は [Agent Harness パターン](/ja/blog/inside-claude-code-agent-harness/)を参照。

## 試したこと、試していないこと

試したこと（Linux x64。OpenCode は無料モデル `deepseek-v4.1-flash-free`、ほかの CLI はローカルの mock に向けるかコマンドラインでの確認のみ。実アカウントは使っていない。時刻はすべて UTC+8）：

![今回インストールした各 CLI のバージョン](/assets/opencode-2-4-automations-mcp-events/install-versions.webp)

- OpenCode 2.4.1：`every` トリガーの shell と prompt アクション、HTTP API の制限、TUI の `/automation` と shell の確認、`ask` と `deny` ルール、`automations: false` と再有効化、pause と resume、server 再起動後の永続化。
- MCP：自作の stdio server で、プッシュ配信の購読からファイル書き込みまでの全経路。`protocol` なし、`legacy`、`2026-07-28`、v1 フラット形式の四通りのハンドシェイク。エラーコードを返さない server でのフォールバック時間。
- プラグイン：ローカル npm registry での `^1.0.0` と固定バージョンの更新、範囲外の版、読み込み失敗時のロールバック。
- Copilot：OpenCode 2.3.2 と 2.4.1 で、`GITHUB_TOKEN` だけの場合と `COPILOT_GITHUB_TOKEN` を設定した場合の provider 一覧。
- ハンドシェイクの比較：Claude Code 2.1.331 と Codex 0.172.0 はセッション内の接続、Gemini CLI 0.71.1 と Qwen Code 0.28.4 は `mcp list`。

試していないこと：

- `cron` と `at` トリガー、`code` アクション、イベントのポーリングと webhook 配信。
- 24 時間ごとの定期確認（手動の確認で代用）、Git ブランチと `semver:` 範囲のプラグイン。
- `generate_image` と `generate_video` の実際の生成、Desktop アプリ、実際の Copilot ログイン。
- `ask` ルールのもとで HTTP から shell automation を作った場合の挙動。
- Amp の機能全般、Gemini CLI と Qwen Code の実セッションでのハンドシェイク、Codex App の automation。
