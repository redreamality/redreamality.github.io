## TypeSafe Jev 深度调研

调研日期：2026-09-18。性质：技术选型研究，不是 API 实测报告。未申请账号、使用密钥或调用付费接口。本文区分官方接口事实、厂商自测与作者推论；资料可用性不等于性能已经独立复现。

### 结论

Jev 最值得关注的不是“更便宜的聊天模型”，而是把自然语言判断做成可被代码调用的概率接口。建议以低风险影子流量试用，不建议因为“零幻觉”宣传就授予它执行权限。

TypeSafe 在 2026-09-15 宣布早期访问。其技术路线自述为新架构、并行输出和 RLCD（Reinforcement Learning for Calibrated Decisions）。本次查阅材料解释了产品行为与训练目标，但没有提供足以复现训练的完整算法、权重与实验细节。[S1][S2]

### 一、它到底返回什么

输入由 state 和 questions 组成：前者放材料，后者定义要判断的问题与允许的答案。它不负责生成开放式回答。[S3]

| 原语 | 语义 | 需要防止的误解 |
| --- | --- | --- |
| Choice | 在给定候选中选一个，并返回候选概率 | 必须考虑“没有合适选项”；相对排名不是绝对适用性 |
| Noul | 返回某个是非命题成立的概率 | 不是自带 confidence 的 Choice；多条 Noul 不自动互斥 |
| Score | 对有序文字等级给出分布及等级索引的期望 | 不是精确测量，也不是任意数值回归 |

原语依据：[S4][S5][S6]。

一个原创示例：处理用户的工具请求时，同时问“是否需要外部数据”“是否有写入副作用”和“最合适的工具是什么”。代码检查授权与参数，再决定调用、拒绝或复核。模型提供判断信号，程序拥有控制流。

抽取也需要换一种思路：先用解析器得到候选字符串，再让 Jev 选择候选 ID。它不能直接替代要求任意文本输出的抽取器。官方故障说明明确建议这种候选选择方式。[S7]

### 二、架构意义与未知项

官方提出的差异不是给聊天结果套 JSON，而是把输出目标收窄到决策及其分布，并对共享 state 的多个问题并行评估。[S1][S2][S8]

我的判断：如果工作负载确实主要由短小、独立的语义判断组成，这种设计具有合理的效率动机。但接口结构不能证明底层一定采用某种编码器、分类头或蒸馏方案，不能自行补全未公开的实现。

需要继续向厂商索取：

- RLCD 的损失函数、奖励信号、概率监督来源和训练消融。
- 架构、参数规模、训练语料构成，以及和传统判别模型的对比。
- 按语言、领域、类别数划分的校准结果。
- 稳定性、吞吐、尾延迟、版本生命周期及故障恢复承诺。

这些是本次查阅没有充分回答的问题，不是“官方一定没有”的断言。

### 三、概率与 confidence 不能混用

Choice 和 Score 的 confidence 是由答案概率分布计算的统计量，Noul 没有该字段。它概括分布形状，不等于一个独立预测的“答对概率”。官方概念页没有给出具体计算公式，不能擅自假设为最大概率或归一化熵。[S9]

校准应理解为一组预测的统计性质，不是对单个事件的保证。[S2]

我的工程判断：

- 分布很尖锐仍可能指向错误答案；高 confidence 不是业务正确性的证明。
- 换候选集、问题措辞、语言或模型版本后，旧阈值需要重新验证。
- 类别相对概率不能直接用作“这个任务一定需要某工具”的判断。
- 多个独立问法之间的概率不能随意相乘；并行计算不证明事件独立。
- 添加“不适用”和“信息不足”选项，避免答案空间强迫错误选择。

Score 也存在信息压缩：`score = Σ(level_index × probability)`。同一个均值可以来自集中在中间等级，也可以来自两端各占一半；涉及风险时应检查完整分布。[S6]

### 四、“零幻觉”的实际边界

发布文把 0% 建立在 schema 匹配保证上，而非全面事实核验。[S1]

因此应分开验收：

| 验收层 | 应问的问题 |
| --- | --- |
| 类型 | 返回的字段与枚举是否合法？ |
| 语义 | 选中的答案是否符合证据？ |
| 业务 | 是否满足权限、政策与先决条件？ |
| 执行 | 是否幂等、可回滚，有没有外部副作用？ |

这是分析框架，不是 Jev 提供的四项保证。假设退款选项只有“允许/拒绝”，返回“允许”在类型上完全合法，却可能是一次错误决策。

官方还承认 `jev-1.13` 易受对抗性 state 影响；计数、日期比较、多跳理解、大量无关上下文和跨问题一致性也有边界。[S7]

建议把数学、时间、权限和事务约束留在确定性代码里。把 Jev 用作辅助检测器可以，把它作为唯一安全屏障不合适。

### 五、性能证据究竟说明什么

官方首页宣传 193.6 倍更快、444.6 倍更便宜。发布文承认这些是其工作流比较中的较高收益，并指出短输入示例有利于 Jev、测速主要从美国西海岸进行、LLM 概率包装增加了对照组开销。[S1]

截至调研日，官方评测站展示四类工作流，按工作流等权平均。参考标签来自 GPT-6 Astra 与 Claude Fable 5.1 的高思考设置，其他模型使用供应商默认推理设置。[S10]

以下直接记录页面显示值，价格和耗时存在展示舍入：

| 模型，均为 workflow 路径 | 参考标签一致率 | 美元/案例 | 秒/案例 |
| --- | --- | --- | --- |
| Jev | 67.8% | 0.0004 | 0.4 |
| terra | 67.9% | 0.0304 | 10.1 |
| sonnet 5 | 67.8% | 0.1174 | 78.1 |
| sol | 74.1% | 0.0836 | 23.3 |

重要反例：发票工作流上 Jev 为 61.8%，sol 为 79.1%。因此平均质量接近某个模型，不等于所有任务都接近；低成本优势也不等于质量领先。[S10]

我对证据的评级：

- 对“在这些固定工作流里速度与成本明显较低”：厂商数据支持，仍需独立复现。
- 对“达到所有前沿模型的能力”：证据不足。
- 对“达到无人值守业务所需正确率”：不能从模型共识标签推出。
- 对“所有线上任务都有百倍收益”：不支持这种外推。
- 对“代码拆解比一个大提示更有效”：在本评测均值上成立，但同样惠及对照模型，不是 Jev 独有收益。

还要区分 API 延迟与完整业务延迟；检索、解析、数据库、重试和人工复核不会因为推理变快而自动消失。

### 六、成本与实际采购

公开标价为每十亿输入 token 42 美元，即每百万 0.042 美元，输出不计费。[S1][S11]

算例，而非实测账单：若每次总计费输入恰好 1,000 token，一百万次调用的模型输入费用约 42 美元。这里必须包括问题和选项等实际计费输入，不能只算用户正文。

建议按下面的业务口径验收，而不是只比 token：

`总成本 = Jev 调用 + 检索解析 + 重试 + 大模型回退 + 人工复核 + 错误损失`

可批量共享同一 state 的问题越多，越值得研究并行调用；但没有理由为了“并行免费”把大量无关问题硬塞进每次请求。官方有并行问题 cookbook，可作为实验起点，不能直接当作所有场景的加速保证。[S8]

接入与可用性详见同目录 `2026-09-18-jev-api-notes.md`。在合同确认前，不应把公开标价、示例响应时间或 SDK 的重试能力视为生产 SLA。

当前模型页的实际约束：[S11]

- 模型版本为 `jev-1.13.0`；`jev-latest` 和 `jev-preview` 当前都指向它。
- 只接收文本或文本的结构化表示，不原生接收图像、音频、视频。
- 请求总预算为 64k tokens，另有 `state + 最长问题 <= 32k` 的约束。
- 公布的速率限制为每分钟 1,200 次请求，但明确可能动态调整。
- 英语是主要训练语言且表现最好，中文等 CJK 语言不能假设具有同等质量。
- 没有按客户提供模型微调或 LoRA；领域适配通过输入状态与问题定义进行。

商业边界同样重要：不训练客户请求不等于默认零保留，企业 ZDR 需要另行联系。[S12] MCA 第 2.3(f) 项限制客户发布 benchmark/性能信息，第 2.3(h) 项还涉及安全或漏洞测试限制。计划公开实测或开展安全测试前，应向厂商确认适用合同和授权范围；这里是条款提示，不是法律意见。[S13]

### 七、适合怎样的 Agent 系统

下面是结合接口边界提出的选型建议，而非经过本次实验验证的收益：

| 场景 | 建议 | 关键边界 |
| --- | --- | --- |
| Skill/工具路由 | 优先试验 | 候选已知；保留不调用路径；权限由代码判断 |
| 检索材料筛选 | 优先试验 | 评估误删关键证据的概率，而不只是排名 |
| Agent 运行记录复核 | 影子模式试验 | 不能把“没有告警”解释为已证明安全 |
| 内容标签、工单分类 | 优先试验 | 中文和混合语言需独立样本 |
| 引用核查 | 辅助检查 | 必须提供原文；可辅助发现问题，不能保证事实真实性 |
| 长篇写作、代码生成 | 不匹配 | 不输出自由文本 |
| 精确运算、日期先后 | 用代码 | 官方列出的能力弱项 |
| 执行转账、删除、发布 | 不作唯一裁决器 | 授权、确认、审计、回滚都需要独立实现 |

值得试验的结构：

```text
输入
  -> 确定性过滤、检索、候选构造
  -> Jev 并行语义判断
  -> 程序校验权限与业务约束
  -> 达到经验证门槛：执行低风险动作
  -> 未达门槛或失败：大模型、人工、拒绝或补充信息
```

无论 confidence 多高，都不绕过授权。网络失败、超时、字段异常必须有独立失败路径，不要把错误默认映射为“允许”。

### 八、建议的验证方案

以下为实验设计，不是已经完成的测试：

前提：获得账号访问许可；涉及公开性能报告或安全测试的部分，先确认合同和书面授权。

1. 准备约 1,000 条真实历史任务作为首轮试验，按中文、英文、中英混合、歧义、信息不足和恶意输入分层；高风险低频错误可能需要远大于此的样本。
2. 由人工和确定性业务规则建立标签，记录分歧；不能直接把强模型输出全部当真值。
3. 设定基线：现有规则、适配任务的传统分类器或重排器、成本接近的小模型，以及当前线上模型。
4. 在相同材料和任务定义下比较；既测原生概率接口，也测业务实际所需的最小输出，不只让对照模型生成完整概率 JSON。
5. 使用开发集调阈值，使用独立测试集验收，避免在同一批数据上调参和报分。
6. 统计按类 precision/recall、校准曲线、Brier score、固定错误预算下的自动处理覆盖率，并附样本量及区间。
7. 测 P50/P95/P99 端到端延迟、并发、错误率与重试成本；从实际部署地域发请求。
8. 加入选项重排、语义改写、无关上下文和提示注入测试，分别记录“高置信但错误”的案例。
9. 固定模型版本，先只记录建议；通过验收后再开放可撤销、低风险动作。

最终选型指标建议为：在业务允许的错误上限内，能自动处理多少真实请求，以及完整系统为此付出多少成本。
